# ReadAloud release checklist

Use this as a go/no-go record. Check an item only after the command, artifact, device test, configuration review or approval has actually passed. Record build IDs, platform/OS version, logs and evidence in the release record. A source change alone does not make a runtime check green.

## 1. Reproducible source and build

- [ ] Commit the npm workspace lockfile generated by a clean, network-enabled install; use `npm ci` from a clean checkout after it exists.
- [ ] Record Node/npm, Python, Rust, Android SDK, Xcode and OS versions used for the release.
- [ ] Run `npm run test:core`, `npm run typecheck`, `python -m pytest apps/api/test` and all production build commands; resolve every failure.
- [ ] Run dependency and license audits for npm, Python and Rust dependencies; review and remediate every high/critical finding and record accepted exceptions.
- [ ] Confirm source has no secrets, local machine paths, debug-only configuration or unintended telemetry.
- [ ] Confirm `main` contains the release candidate and `perez` is synchronized; commits are meaningful and no feature changes remain unmerged.

## 2. Mobile install-size budget and store requirements

- [ ] Produce signed release AAB/APK and IPA using the actual production toolchains.
- [ ] Measure both download size and installed size on representative devices; target **no more than 25 MB installed per mobile app**. Record the exact measurement method and artifact hash. If over budget, profile native libraries, assets and dependency footprint and repeat the measurement after remediation.
- [ ] Verify Android minSdk API 26, target SDK and current Play policy requirements, package ID, version/build number, adaptive icon, launch/splash assets, permission declarations and Data safety answers.
- [ ] Verify iOS bundle ID, supported OS target, icon/launch assets, entitlements, privacy manifest requirements, permission strings, version/build number and App Privacy answers.
- [ ] Supply original store icon, screenshots for supported form factors, short/full descriptions, support URL/contact, privacy-policy URL, age/content rating and region availability.
- [ ] Test installation, launch, upgrade, app data preservation, uninstall/reinstall, low storage and offline behavior on clean devices.
- [ ] Verify accessibility: readable dynamic text, contrast, screen-reader labels/order, touch targets, reduced-motion expectations and clear error/retry states.

## 3. Android and iOS end-to-end acceptance

- [ ] Test on Android API 26 and a current supported Android release, plus a physical Android device.
- [ ] Test on the supported iOS simulator and physical iPhone/iPad form factors selected for release.
- [ ] Import TXT, DOCX, EPUB, text-based PDF, scanned PDF and supported image files; validate every advertised format and explicitly document unsupported cases.
- [ ] Test corrupt, empty, encrypted, malformed, renamed, oversized and archive-bomb documents; verify clear errors without crashes or excessive memory/disk use.
- [ ] Verify indexing progress, cancel/retry behavior, duplicate imports, large books, persistence, deletion and database migration from a prior release.
- [ ] Listen through a long book; verify sentence captions, page preview, pause/resume, seek/skip, voice/rate/volume, position persistence and switching books.
- [ ] Lock the screen, background the app, take calls, disconnect/reconnect Bluetooth and exercise audio focus/interruption/recovery; verify playback and temporary audio cleanup.
- [ ] Test low-memory conditions, repeated imports/deletes, airplane mode, service timeouts, API errors, process death and restart.

## 4. Desktop acceptance

- [ ] Build the Windows NSIS installer on a clean supported Windows environment.
- [ ] Test install, launch, import, long-book playback, local voice, optional API voice, settings, library persistence, upgrade and uninstall.
- [ ] Verify keyboard-only operation, focus visibility, screen reader labels, window resizing and supported minimum window size.
- [ ] Verify Tauri CSP/capabilities are minimal and no unintended filesystem or shell permissions are granted.
- [ ] Sign the installer if required by the distribution channel and verify publisher identity and checksum.

## 5. API, security and operations

- [ ] Deploy behind HTTPS and trusted ingress; set explicit hosts and CORS origins, a high-entropy service token, Redis shared rate-limit storage and request/connection timeouts.
- [ ] Keep Azure credentials in a secret manager, restrict provider permissions, set spend quotas/alerts and test rotation.
- [ ] Confirm API is not exposed with development defaults, production docs are disabled, and logs never contain document text, credentials or audio.
- [ ] Exercise concurrent large uploads, slow clients, rate limits, malformed PDF/ZIP, OCR page/pixel limits, oversized provider output, upstream timeout/failure and Redis outage behavior.
- [ ] Decide the public service access model. A shared static token distributed with a consumer app is extractable and must not be treated as a public-user authentication system.
- [ ] Verify monitoring, alerts, service health, rollback, backups where applicable, incident contact and recovery runbook.
- [ ] Review current npm/Python/Rust dependency advisories and transitive licenses; record fixes or approved exceptions.

## 6. Legal, privacy and store submission

- [ ] Publish a monitored support/legal contact and a stable public privacy-policy URL.
- [ ] Have Terms and Privacy text reviewed against the actual mobile/desktop data flow, Azure processing terms, jurisdictions and applicable consumer/privacy law.
- [ ] Ensure in-app About/Privacy/Terms match actual behavior; explain when files/sentences leave the device and how deletion works.
- [ ] Complete Play Data safety, App Store App Privacy, permissions disclosures, age/content ratings and third-party SDK/provider declarations accurately.
- [ ] Publish the approved license and third-party notices, or keep distribution private until licensing is settled.
- [ ] Review store policies and listing metadata at submission time; do not advertise unsupported formats, offline behavior or voice capabilities.

## 7. Release evidence and go/no-go

- [ ] Attach test logs, test matrix, screenshots, artifact hashes, measured install sizes, signing status, dependency audit output and legal approvals.
- [ ] Verify clean release candidate is merged to `main`, `perez` points to the same commit, working tree is clean in the build environment, and release notes match the actual build.
- [ ] Owner signs off only after every release-blocking item is green. Unverified device, provider, store or legal checks remain blockers—not assumed passes.
