# ReadAloud release verification and end-to-end test plan

**Purpose:** This is the executable acceptance specification for the 0.2.x release candidate. It is deliberately stricter than a smoke test. A case is PASS only when its expected result is observed on the named platform/build and evidence is attached. A source-code inspection, simulator-only result, successful compilation, or test-plan existence is not a runtime pass.

## 1. Test governance

### 1.1 Required environments

Record the exact values for every test run:

- Git commit SHA and release version/build number.
- OS and version; device model; CPU/RAM/storage; screen dimensions.
- Node.js, npm, Expo/EAS, React Native, TypeScript, Python, pytest, Rust/Cargo, Android SDK/Build Tools, Xcode and Tauri versions as applicable.
- Build profile, artifact SHA-256, signing identity and build service ID.
- API deployment URL, API version, region, Redis availability and speech-provider configuration. Never put credentials or document contents in evidence.
- Network profile: normal, high-latency, packet-loss, offline, metered and reconnecting.
- Test account/configuration only if the final release adds accounts. Current design is accountless.
- Result: NOT RUN / PASS / FAIL / BLOCKED; tester; date; evidence link; issue ID; notes.

### 1.2 Pass criteria

A test passes only if every expected result is met, no crash occurs, no sensitive data is exposed, and the result is reproducible. Any crash, data loss, silent corruption, wrong document text, wrong sentence position, stuck playback, unbounded resource use, security bypass or inaccurate privacy disclosure is a release-blocking failure.

Do not mark a test PASS because the code appears to implement it. Do not waive a failure without a documented risk owner, rationale, mitigation and release approval.

### 1.3 Test layers

1. Static validation: formatting/lint where configured, type checks, config validation, dependency and license scans, secret scanning.
2. Unit tests: reader-core, API security/extraction/speech validation, URL/config validation.
3. Integration tests: SQLite/IndexedDB persistence, API multipart parsing, Redis rate limiting, speech provider adapter using deterministic mocks.
4. Platform tests: Android and iOS native builds, permissions, background audio, file picker, local speech, secure storage.
5. End-to-end tests: user journeys from fresh install through import, reading, playback, persistence, delete and upgrade.
6. Operational tests: API deploy, TLS, ingress, rate limiting, monitoring, failure recovery, provider quota and rollback.
7. Store validation: Play Console and App Store Connect forms, signed artifacts, metadata and review access.

- API-040: per-route rate limit returns 429 and Retry-After where configured.

- API-046: provider concurrency and spend caps enforced.
- API-047: provider timeout returns controlled 502/503 without leaking secrets.
- API-048: metrics and logs contain request ID/status/latency but not book text, tokens or provider secrets.

- API-050: health/readiness checks distinguish process liveness from required dependencies.
- API-051: deployment rollback restores previous healthy version.
- API-052: secrets rotated without source changes or client rebuild.
- API-053: alerts fire on error rate, latency, Redis outage and provider quota exhaustion.

**Architecture risk:** the existing single shared API bearer token is extractable from a distributed client. It is not adequate as a public-user identity system. Before a public multi-user speech service is offered, add an appropriate user/session or signed short-lived credential model, abuse attribution, quotas and revocation. If the service remains operator-private, document that limitation and restrict ingress.

If the native runtime and dependencies make it unattainable, report the measured result and revise the target deliberately rather than hiding it.
